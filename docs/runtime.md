# Runtime and generated Go code

The runtime is package `github.com/gopherex/ratel` (`ratel`). `ratel-gen-go`
generates thin packages on top of it: models, table descriptors with typed
columns and relations, reflection-free scanners, insert types, enum types,
type registration and static queries. Everything else is generic runtime code
built on Go 1.27 generic methods.

Models are generated from the schema only (SQL files, or proto through
`protoc-gen-ratel`). There is no Go-first schema: the schema is what
migrations are planned from. Go types a user writes by hand stay the user's;
ratel can scan query results into them (`@go.row`, below) but never derives
schema from them.

## Building and running

Every statement is a value built from a descriptor or a generated query,
without a database: it can be stored, passed around and rendered with
`Build() (sql string, args []any, err error)`, which contacts nothing. `db.Run(q)`
executes it, and the type of `q` decides which verbs exist:

| Built value | Verbs after `db.Run` |
|---|---|
| `app.Users.Select()...`, a write with `.Returning()`, a generated row query | `One`, `First`, `List`, `All`; a SELECT also `Count`, `Exists`, `Chunks` |
| a write without `Returning`, a generated `:exec` / `:execrows` query | `Exec` (affected rows) |

```go
q := app.Users.Update().Set(app.Users.Name.To("Robert")).Where(app.Users.ID.Eq(id))

sql, args, err := q.Build()                     // UPDATE "app"."users" SET "name" = $1 WHERE "id" = $2
n, err := db.Run(q).Exec(ctx)
robert, err := db.Run(q.Returning()).One(ctx)

db.Run(q).List(ctx)               // does not compile: a write without Returning has only Exec
db.Run(q.Returning()).Exec(ctx)   // does not compile: a returning write has only row verbs
```

`db.Run[R any](q Runnable[R]) R` infers the verb set from the built value's
type; `Runnable` has an unexported method, so only runtime types implement it.
Verbs take the context and per-call options (`ratel.ExecMode`). `Returning()`
returns every column of the model; there are no column projections, since a
partially filled model cannot show which fields came from the database.
Projections go through static queries or `Pluck`.

## Executor and DB

```go
// Executor is the only way ratel reaches PostgreSQL.
type Executor interface {
	Exec(ctx context.Context, sql string, args ...any) (pgconn.CommandTag, error)
	Query(ctx context.Context, sql string, args ...any) (pgx.Rows, error)
	QueryRow(ctx context.Context, sql string, args ...any) pgx.Row
	SendBatch(ctx context.Context, b *pgx.Batch) pgx.BatchResults
	CopyFrom(ctx context.Context, table pgx.Identifier, cols []string, src pgx.CopyFromSource) (int64, error)
}

db := ratel.New(exec, ratel.WithExecMode(pgx.QueryExecModeCacheDescribe))
```

- `*pgxpool.Pool`, `*pgx.Conn`, `pgx.Tx` and `github.com/gopherex/pgtx`'s
  `tx.DB` satisfy `Executor` without adapters. *Check:* a compile-time
  assertion test per type.
- ratel creates no pools, opens no connections and has no transaction API.
  Transactions, isolation levels, savepoints for nested units and retry of
  serialization failures come from the executor; with pgtx (v1.1.4 or newer),
  every ratel call inside `Do*` runs in the transaction carried by `ctx`, and
  concurrent use of that transaction from several goroutines is refused with
  pgtx's `tx.ErrTxInUse`, which ratel returns wrapped and unchanged.
- `*ratel.DB` is a concrete type: generic methods cannot be declared on
  interfaces. It is safe for concurrent use when its executor is.
- `WithExecMode` (and the per-call option `ratel.ExecMode(mode)`) passes a pgx
  query exec mode as the first query argument; it is needed behind PgBouncer
  in transaction mode. Default: pgx's default. Eager relation loading uses
  `SendBatch`, whose mode can only be configured on the executor's connections;
  see the explicit-mode restriction under Relations.
- ratel emits no telemetry: no spans, logs or metrics (see Telemetry); pool
  metrics belong to the pool owner.
- There are no hooks or interceptors. Data invariants such as `updated_at`
  belong in the schema (defaults, `BEFORE` triggers): values set by a `BEFORE`
  trigger are returned by `RETURNING`, and they hold for every writer.

## Generated code

Packages follow PostgreSQL schemas: tables, views and types of schema `app`
go to package `app`, file `<out>/app/app.go`; the queries of a query group go to
package `<group>`. The plugin options of `ratel.yaml` are:

| Option | Meaning |
|---|---|
| `import_path` | required: Go import path of the output directory; packages import each other through it |
| `types` | PostgreSQL type name (`jsonb`, `app.money`) to a Go type (`github.com/acme/doc.Document`), replacing the default mapping |

`@go.type <import/path.Type>` on a column overrides its Go type; other `go`
annotations are `@go.row` (below). Every generated file starts with
`// Code generated by ratel-gen-go. DO NOT EDIT.` and is gofmt-formatted.
A domain is a Go alias of its base type's Go type (PostgreSQL enforces its
constraints); an enum is a string type with one constant per label; a
composite is a struct of `ratel.Null` fields. Generated and `GENERATED ALWAYS`
identity columns are absent from the insert type: PostgreSQL computes them.
Every named constraint gets a sentinel `Err<ConstraintName>` matched with
`errors.Is` against write errors.

```go
type User struct {
	ID        int64
	Email     string
	Status    UserStatus      // enum type generated from the Catalog
	ManagerID ratel.Null[int64] // nullable column
	CreatedAt time.Time
	R         UserRelations     // loaded relations, tri-state
}

func (u *User) Orders() ([]Order, error) // ratel.ErrNotLoaded unless loaded

// Row starts an insert row; each required column is one step, in column order.
func (t *usersTable) Row() userRowEmail
func (s userRowEmail) Email(v string) userRowStatus
func (s userRowStatus) Status(v UserStatus) UserInsert

type UserInsert struct {
	email     string               // NOT NULL, no default: a Row step
	status    UserStatus           // NOT NULL, no default: a Row step
	valid     bool                 // set only by the last Row step
	managerID ratel.Null[int64]    // nullable, no default: zero value inserts NULL
	id        ratel.Opt[int64]     // identity: omitted unless set
	createdAt ratel.Opt[time.Time] // DEFAULT now(): omitted unless set
	// a nullable column with a default would be ratel.Opt[ratel.Null[T]]
}

// Optional columns, in any order; each returns a modified copy and takes the
// model field's type (Null[T] for a nullable column).
func (r UserInsert) ManagerID(v ratel.Null[int64]) UserInsert
func (r UserInsert) ID(v int64) UserInsert
func (r UserInsert) CreatedAt(v time.Time) UserInsert

var Users = &usersTable{...}      // descriptor: immutable, dependency-free, generated code only

type usersTable struct {
	ratel.WriteTable[User, UserInsert]
	ID        ratel.Col[User, int64]
	Email     ratel.Col[User, string]
	Status    ratel.Col[User, UserStatus]
	ManagerID ratel.NullCol[User, int64]
	CreatedAt ratel.Col[User, time.Time]
	Orders    ratel.Rel[User, Order]
	Manager   ratel.Rel[User, User]
}

// only in a package with composite, custom range or custom array types (below)
func RegisterTypes(ctx context.Context, conn *pgx.Conn) error // for pgxpool AfterConnect
```

Rules:

- The model is a plain struct; columns, scanner and relations live in the
  descriptor. Nullable columns are `ratel.Null[V]` fields in the model and
  `NullCol[M, V]` in the descriptor, so operators take `V`
  (`ManagerID.Eq(int64)`, `IsNull()`).
- Optional values are value types, never pointers:
  - `ratel.Null[T]`: a value or SQL NULL; exported fields `V T` and
    `Valid bool` (the shape of `pgtype` and `sql.Null`), constructors
    `ratel.NullFrom(v)`, `ratel.NullFromPtr(p)`, and `Ptr() *T`;
  - `ratel.Opt[T]`: set or not set (not set = the column is omitted and its
    default applies); exported fields `V T` and `Set bool`, constructor
    `ratel.OptFrom(v)`;
  - both implement `IsZero()` (NULL, respectively not set), so JSON's
    `omitzero` skips them, and scan and encode through pgx codecs natively,
    without `database/sql` interfaces.
- Non-null columns are plain fields: a wrapper would add a state the column
  cannot have.
- One model type per table, shared by the builder and by static queries.
  There are no bridge conversions between model kinds.
- Scanners and argument lists are generated code. *Check:* the linter forbids
  importing `reflect` in package `ratel` and in code generated by
  `ratel-gen-go`.
- Required columns (NOT NULL, no default, not identity or generated) are set
  through `Row()`: one unexported step type per required column, in column
  order, each with exactly one method naming its column. Only the last step
  returns `UserInsert`, so a row missing a required column has another type
  and does not compile as an insert; values cannot be swapped between columns
  of the same Go type. A table without required columns has `Row()` returning
  `UserInsert` directly. Go still allows the zero literal `UserInsert{}`; the
  last step sets an unexported flag, and every write rejects a value without
  it with `ratel.ErrInvalidInsert` before any SQL is sent. Optional columns
  (nullable without default, `ratel.Opt` for a default, identity or generated
  value) are setter methods on `UserInsert`.
- Enums come from the Catalog: a PostgreSQL enum type, or a `text`, `varchar`
  or `char` column with a `CHECK (column IN ('a', ...))` of string literals,
  becomes a Go string type with one constant per value; the column's type is
  `<Model><Column>` (`TagKind`, constants `TagKindTopic`, ...) unless
  `@go.type` overrides it. pgx sends and reads a scalar enum as text without
  registration; arrays carry enum values as `string` (above).
- Views and materialized views get a model and a read-only descriptor (no
  write methods).
- Composite primary and foreign keys are supported everywhere; batched loading
  binds them as parallel arrays through `unnest($1::t1[], $2::t2[])`.
- A table without a primary key has `Update().Where()` and `Delete().Where()`
  but nothing that addresses one row by identity: its descriptor embeds
  `ratel.WriteTable[M, I]`, while a table with one embeds
  `ratel.KeyedTable[M, I]`, the only type with `Save` and `DeleteRow`, so
  misuse does not compile; nor is it a relation target.
- Generated identifiers come from one naming function (singular model, plural
  descriptor, Go initialisms). A collision is a generation error naming both
  sources, never a silent suffix.
- Scalars, enums, domains, `numeric` and nullable or optional values need no
  connection setup: `ratel.New(pool)` is all a package without the types
  below requires. `RegisterTypes` exists only in a package whose columns,
  parameters or results use a composite type, a range or multirange of a
  non-built-in type, or an array of an enum, domain or composite:
  PostgreSQL assigns their OIDs per database, so pgx loads them per
  connection. It loads those types and calls `ratel.RegisterValue` for the
  `Null` fields of composites.

### Descriptor construction

Generated read-only descriptors embed `ratel.Table[M]`, initialized with
`ratel.NewTable(schema, table, columns, scan, options...)`. Physical-table
descriptors embed `ratel.WriteTable[M, I]`, constructed with
`ratel.NewWriteTable(table, validInsert, fields...)`, or, with a primary key,
`ratel.KeyedTable[M, I]` from `ratel.NewKeyedTable(writeTable)`. The table
options `ratel.PrimaryKey(columns, values)` and `ratel.ModelValues(func(M)
[]any)` (every column's model value in column order, used by `Save`) are
generated projections, never reflection. `validInsert` reads the
insert type's private constructor flag. Each generated `ratel.InsertField[I]`
supplies `Name`, a schema-qualified PostgreSQL `Type` (`pgx.Identifier`), and
`Value func(I) (any, bool)`: the boolean says whether to include the column.
Required and nullable-without-default columns always return true; defaulted
columns return their `Opt.Set` and unwrap `Opt.V`, including `Opt[Null[T]]`.
`Set func(I) bool` answers the same question without boxing the value: rows
are grouped by their set columns through it without allocations, and `Value`
runs only for the parameters of a `VALUES` statement. Generated fields always
supply it; a nil `Set` falls back to `Value`'s flag.
Scalar fields also provide `Values func([]I) any`, projecting rows into a native
typed slice for pgx (for example `[]string`, `[]int64`, or `[]pgtype.Text` for
nullable text). Its length must equal the input length and preserve row order.
Native typed arrays are required: `FlatArray[any]` has no default PostgreSQL
type in exec/simple-protocol mode. Generated registration supplies default pgx
array mappings for custom Go types used by these projections, as well as their
scalar codecs. Array-valued columns set `Array: true`; their `Type` names the
PostgreSQL array type and `Values` is unused. Metadata and field projections
are generated, never reflected.
Only `WriteTable` implements `ratel.Writable[M, I]`; passing a view, materialized
view, static query or SELECT to a DB write method fails to compile.

`columns` lists the
PostgreSQL output names in scanner order. The generated
`ratel.Scanner[M]` has signature `func(pgx.Row) (M, error)` and calls `Scan`
with explicit model-field addresses. `ratel.NewCol[M, V](name)` and
`ratel.NewNullCol[M, V](name)` construct its typed column fields. Columns
refer to the current source's output names; the renderer binds and quotes its
alias independently from the descriptor's physical schema.

`ratel.PrimaryKey(columns, func(M) []any)` supplies the ordered primary-key
columns and their generated field projection. These keys are non-null and
unique. Views omit this option unless their result has a proven unique,
non-null key. Static `NewQuery` sources carry no primary-key metadata and
cannot use `Chunks`; a nested builder SELECT preserves its source's key.
Constructor inputs are copied;
descriptors and SELECT builders are immutable and can be shared concurrently.
Table descriptors precompute their quoted projection and plain SELECT SQL.
`InSchema` recomputes schema-dependent SQL;
rendering an unmodified table SELECT reuses its SQL without a per-call cache.
The caller must not mutate argument values (for example, bound slices) while
an operation uses them, following pgx's argument ownership rules.

Generated table and view descriptors are pointers (`var Users = &usersTable{...}`):
`Select`, `Insert`, `Upsert`, `Update`, `Delete`, `Save` and `DeleteRow` are
methods of the embedded runtime table, and sources such as `Select().From(...)`
take descriptors as interfaces, which then hold the pointer, where a value
descriptor would be copied to the heap on every call.
A generated descriptor provides its own `InSchema(schema)` method: copy the
whole descriptor, replace its embedded `Table` with `Table.InSchema(schema)`
(or `WriteTable` with `WriteTable.InSchema(schema)`), and return a pointer to
that copy. This preserves typed columns, insert metadata and relation fields.

The last parameter step of a generated row query returns
`ratel.NewQuery(columns, scan, sql, args...)`, an `:exec` query
`ratel.NewCommand(sql, args...)`. SQL is trusted generated SQL with contiguous
`$1..$n` parameters, no trailing statement delimiter, and schema-qualified
physical table references. It is embedded unchanged; outer builder predicates
continue parameter numbering. `db.Run(query)` runs the query's statement
verbatim, so DML with `RETURNING`, which cannot be a subquery, runs too; there
`One` and `First` add no `LIMIT` and stop reading after two rows and one row.
`query.Select()` starts a SELECT over the query's result, and a builder SELECT
also implements `ratel.Source[M]`, so `ratel.From(selectBuilder)` nests it
while preserving its result model and scanner.

### Nullable and optional pgx values

`Null[T]` and `Opt[T]` never reach pgx as values, so they need no connection
setup:

- Arguments: generated code and the builder pass pgx `nil` for NULL and `V`
  otherwise (`Null.Arg()`); a set `Opt` passes `V`, an unset one omits its
  column. `NullCol.To(Null[V])` unwraps the same way.
- Results: a generated scanner reads a nullable column into a pgx-native
  nullable target and builds the `Null[T]` from it: `pgtype.Bool`, `Int2`,
  `Int4`, `Int8`, `Float4`, `Float8`, `Text`, `Timestamptz`, `Timestamp`,
  `Date` and `UUID` for the matching built-in Go types and for enums (through
  `pgtype.Text`), and `*T` for every other type, which pgx allocates only for
  a non-NULL value. `PluckNull` reads through `*V` the same way.
- Arrays sent by inserts and relation loads carry pgx-native elements: `*T`
  for nullable values, and enum values as `string`; the SQL casts the array
  to the column type, as in `unnest($1::text[]::"app"."user_status"[])`, so
  pgx encodes a built-in array type. `InsertField.Base` and `RelKey.Base` name
  that wire type; when empty, `Type` is sent as is.

`ratel.RegisterValue[T](typeMap, name)` remains for values pgx itself scans
field by field: the fields of generated composite types (`Null[T]` inside a
struct read by pgx's composite codec), and handwritten code that scans into
`Null[T]` or `Opt[T]` directly. It decorates the existing `pgtype.Codec`,
preserving its formats and configuration; encoding uses `V`, scanning `&V`,
and the runtime still neither imports `reflect` nor implements
`database/sql.Scanner` or `driver.Valuer`. A `TryWrapScanPlanFuncs` hook alone
is insufficient: pgx v5.11 calls the codec first, and its JSON codecs would
marshal the wrapper's fields. Call it on every connection before queries,
after loading the PostgreSQL type; a missing type name returns
`ratel.ValueTypeError`.

- Invalid `Null[T]` is SQL NULL without inspecting `V`. Scanning SQL NULL
  clears `V` and `Valid`; non-NULL input sets `Valid` only after a successful
  scan. JSON `null` is not SQL NULL: `Valid` remains true.
- Unset `Opt[T]` is omitted from generated writes so the column default
  applies. Encoding it directly through `RegisterValue` returns
  `ratel.UnsetOptError`; unset never silently becomes SQL NULL.
- `Null[T]{Valid: true}` and `Opt[T]{Set: true}` do not override `T`'s native
  NULL semantics: a nil pointer or a nullable pgtype value still encodes NULL.

### Type mapping

| PostgreSQL | Go |
|---|---|
| `int2`, `int4`, `int8` | `int16`, `int32`, `int64` |
| `float4`, `float8` | `float32`, `float64` |
| `numeric` | `decimal.Decimal` (`github.com/shopspring/decimal`), encoded and scanned through its `database/sql` methods; `pgxdecimal.Register(conn.TypeMap())` from `github.com/jackc/pgx-shopspring-decimal` in `AfterConnect` switches to the binary codec |
| `text`, `varchar`, `char` | `string` |
| `bool` | `bool` |
| `bytea` | `[]byte` |
| `uuid` | `uuid.UUID` (`github.com/google/uuid`) |
| `timestamptz`, `timestamp`, `date` | `time.Time` |
| `time` | `pgtype.Time` |
| `interval` | `pgtype.Interval` (months and days are not durations) |
| `inet`, `cidr` | `netip.Addr`, `netip.Prefix` |
| `json`, `jsonb` | `json.RawMessage`, or the type from `@go.type` |
| ranges, multiranges | `pgtype.Range[T]`, `pgtype.Multirange[...]` |
| arrays | slices of the element type |
| enum, composite, domain | generated types |

Every mapping can be overridden in the plugin options per type or per column
(`@go.type`). An override type must have a pgx codec or implement
`database/sql`'s `Scanner` and `driver.Valuer`; a codec that needs registration
is registered by the application in `AfterConnect`.

## Static queries

Query files are grouped into Go packages in `ratel.yaml`
([cli.md](cli.md)); every named query becomes a function there that starts
building it. Each parameter is one step, in order of first appearance, with a
method named after the parameter; only the last step returns the runnable
query, so a parameter cannot be skipped or swapped with another of the same
type. A query without parameters returns the runnable query directly.

```sql
-- name: OrdersInRange :many
SELECT * FROM app.orders WHERE user_id = @user_id AND total BETWEEN @min_total AND @max_total;
```

```go
func OrdersInRange() ordersInRangeUserID
func (s ordersInRangeUserID) UserID(v int64) ordersInRangeMinTotal
func (s ordersInRangeMinTotal) MinTotal(v decimal.Decimal) ordersInRangeMaxTotal
func (s ordersInRangeMaxTotal) MaxTotal(v decimal.Decimal) ratel.Query[app.Order]

q := users.OrdersInRange().UserID(ann.ID).MinTotal(lo).MaxTotal(hi)
sql, args, err := q.Build()
orders, err := db.Run(q).List(ctx)
```

Result types are chosen by the provenance of the result columns (inferred
source columns, not names), so `Row` types appear only when nothing existing
fits:

| Select list | Go result |
|---|---|
| every column of one table, any order | the table model; the scanner follows the query's column order |
| every column of one table plus computed columns | `<Query>Row { app.User; OrderCount int64 }` |
| every column of several tables | `<Query>Row { Order app.Order; User *app.User }`; a field is named after its model, or after the alias when one table appears twice; a table on the nullable side of an outer join is a pointer, `nil` when its first primary-key column is NULL |
| anything else | `<Query>Row` with one field per column |
| any shape, query annotated `@ratel.row <Name>` | shared type `<Name>`; every query with that name must have the same shape, else a generation error |
| any shape, query annotated `@go.row <import path>.<Type>` | the user's own struct; each column scans into the field named after it, so the Go compiler rejects a missing field or a type mismatch when the generated package builds. The plugin stays a pure function of its request and reads no user code |

Inference supplies this decision through `QueryColumn.source_column` and
`table_alias`, not through output labels. Selecting `u.id AS other_id` keeps the
identity of `u.id`; computing `u.id + 1 AS id` does not. Aliases distinguish
self-join instances, while column nullability records outer-join effects.
`@ratel.row` and `@go.row` remain query metadata for the output plugin; they do
not change PostgreSQL type inference or manufacture column provenance.

Two queries with identical shapes and no `@ratel.row` produce warning
`RTL-G10` that suggests one.

- `:one` and `:many` build a `ratel.Query[M]`: the caller picks `One`,
  `First`, `List` or `All` after `db.Run`; `One` returns `ratel.ErrNotFound`
  for no row and `ratel.ErrMultipleRows` for more than one. `INSERT`, `UPDATE`
  and `DELETE` with `RETURNING` are row queries too and run verbatim.
- `:exec` and `:execrows` build a `ratel.Command`, whose only verb is `Exec`
  (affected rows).
- `:copyfrom` takes `INSERT INTO t (columns) VALUES (parameters)` and generates
  `<Query>(ctx, db, rows iter.Seq[<Query>Params]) (int64, error)` streaming the
  rows through COPY (`db.Copy`); COPY has no SQL to build, so it is the one
  generated function that executes.
- Nullable parameters take `ratel.Null[T]`. Unnamed `$N` parameters are
  `ArgN` steps.
- A query package has its own `RegisterTypes` under the same rule as table
  packages. `@go.row` structs are the user's: their fields scan as pgx scans
  them, so a `Null[T]` field there needs `ratel.RegisterValue`.
- Arrays of scalars and of composite types map natively. `json` and `jsonb`
  values get a Go type only through `@go.type`; ratel does not guess the shape
  of JSON built in SQL.

### Queries as builder sources

Every `:one` and `:many` `SELECT` query also gets a column descriptor
`<Query>Q`, so runtime filters, ordering and pagination can be added to SQL
that the builder does not express (CTEs, window functions, aggregates):

```go
active := users.ActiveUsers().Since(since).Select().
	Where(users.ActiveUsersQ.Email.Like("%@acme.com")).
	OrderBy(users.ActiveUsersQ.CreatedAt.Desc()).Limit(20)
list, err := db.Run(active).List(ctx)
```

- It renders `SELECT ... FROM (<query>) q WHERE ... ORDER BY ... LIMIT ...`;
  the query's parameters keep `$1..$n` and the builder's continue from `$n+1`.
- Added clauses apply to the query's **result**: when the query itself has
  `LIMIT`, aggregates, window functions or `DISTINCT ON`, a filter added
  outside narrows that result, it does not run before them. This is the defined
  meaning and is stated in the generated doc comment of such descriptors.
- The builder itself has no CTE API; complex shapes are written in SQL and
  composed this way.

## Query builder

```go
u, err := db.Run(app.Users.Select().Where(app.Users.Email.Eq(email))).One(ctx)
us, err := db.Run(app.Users.Select().Where(app.Users.Status.In(app.UserActive)).
	OrderBy(app.Users.ID.Asc()).Limit(100)).List(ctx)
for u, err := range db.Run(app.Users.Select()).All(ctx) { ... }
ids, err := db.Run(app.Users.Select().Pluck(app.Users.ID)).List(ctx)  // []int64
n, err := db.Run(app.Users.Select().Where(...)).Count(ctx)
sub := ratel.From(app.Users.Select().Where(...)).OrderBy(...)       // SELECT over a SELECT
```

- `Where` takes `ratel.Cond[M]` for the query's model only; a condition on
  another table does not compile. `Join(source, on)` inner-joins another
  descriptor, static query or SELECT on a `ratel.Cond2[M, M2]`
  (`app.Users.ID.EqCol(app.Orders.UserID)` style column comparisons) as
  `"j0"`, `"j1"`, ...; the result stays `M`, and a row repeats once per match,
  so existence is `rel.Has`. A static query joins only while no earlier
  argument is bound, since its own markers start at `$1`.
- `Col[M, V]` has comparison, `In`, range and pattern operators typed by `V`;
  `NullCol[M, V]` adds `IsNull` and `IsNotNull`.
- `app.Users.Select()` starts a SELECT over a descriptor, `query.Select()`
  over a static query, and `ratel.From(source)` over any `ratel.Source[M]`,
  including another SELECT.
- Verbs after `db.Run`: `One` (exactly one row; `ErrNotFound` for zero,
  `ErrMultipleRows` for more than one), `First` (at most one row;
  `ErrNotFound` for zero), `List` (slice), `All` (`iter.Seq2`),
  `Count` and `Exists` (over the result, after `Limit` and `Offset`:
  `SELECT count(*) FROM (<select>)`), and `Pluck(col)` (non-null column, values
  `V`) or `PluckNull(col)` (nullable column, values `Null[V]`) with `List` and
  `All`; `Pluck` is part of the built value, so it renders through `Build`.
  `One` requests at most two rows; `First` requests at most one. Neither
  increases an existing lower limit. Without `OrderBy`, `First` uses
  PostgreSQL's unspecified row order. `List` returns a non-nil empty slice
  for an empty result and no partial slice on failure. `All` is lazy, closes
  its cursor on exhaustion, failure or early break, and yields an error once
  with a zero model. Every terminal accepts per-call options after its
  context argument.
- `Build()` returns the SQL text and its ordered arguments without executing.
  Invalid metadata or negative pagination returns `ErrInvalidQuery` before
  contacting the executor. Identifiers are always quoted; limit and offset
  are numbered parameters, and zero limit means no rows.
- Conditions support `Eq`, `Ne`, `Lt`, `Lte`, `Gt`, `Gte`, `In`, `NotIn`,
  `Between`, `Like`, `NotLike` and `ILike`, with `And`, `Or` and `Not`
  preserving grouping. Empty `In` is false; empty `NotIn` is true. The zero
  `Cond` and `Cond2` are true. Nullable column comparisons take the underlying
  value, not `Null[V]`, and follow SQL's three-valued logic. Repeated `Where`
  clauses are conjoined; repeated `OrderBy` calls append ordering terms.
  Column comparisons (`EqCol`, `NeCol`, `LtCol`, `LteCol`, `GtCol`, `GteCol`)
  produce `Cond2[M, N]`; its `SQL(leftAlias, rightAlias)` binds independent
  aliases. Even `Cond2[M, M]` is a join predicate, not a `Where` condition.
- Projections into other shapes go through queries with `@ratel.row` or
  `@go.row` used as builder sources, or through `Pluck`.
- Pagination: `Limit`, `Offset`, and keyset `After(values...)`: one value per
  `OrderBy` term, continuing after that row in the given directions (expanded
  to `c1 > v1 OR (c1 = v1 AND c2 > v2)`, with `<` for descending terms). Keyset
  columns are non-null; another number of values than terms is
  `ErrInvalidQuery`.
- Locking: `ForUpdate`, `ForShare`, with `SkipLocked` and `NoWait`; a wait
  policy without a lock is `ErrInvalidQuery`.
- Escape hatch: `ratel.Raw[M](sql, args...)` yields a `Cond[M]` fragment that
  references columns as `"q"."column"`; its `$N` markers are renumbered by the
  builder, markers inside literals, quoted identifiers, dollar-quoted strings
  and comments stay, and a marker without an argument is `ErrInvalidQuery`.

## Writes

```go
insert := app.Users.Insert(
	app.Users.Row().Email(email).Status(status),
	app.Users.Row().Email(other).Status(status).ID(7),
)
created, err := db.Run(insert.Returning()).List(ctx)
n, err := db.Run(app.Users.Upsert(rows...).OnConflict(app.Users.Email).
	Update(app.Users.Status)).Exec(ctx, ratel.ExecMode(pgx.QueryExecModeExec))
user, err := db.Run(app.Users.Update().Set(app.Users.Status.To(status)).
	Where(app.Users.Email.Eq(email)).Returning()).One(ctx)
n, err = db.Run(app.Users.Delete().Where(app.Users.Email.Eq(email))).Exec(ctx)
n, err = db.Run(app.Users.Save(user)).Exec(ctx)
```

- `app.Users.Insert(rows...)` and `app.Users.Upsert(rows...)` accept only the
  table's generated insert type. Every constructor flag is checked before
  any SQL is sent, including rows in later chunks; an empty input also returns
  `ErrInvalidInsert`. Unset optional columns are omitted, never bound as NULL.
- `OnConflict(cols...).Update(cols...)` assigns `EXCLUDED` values;
  `OnConflict(cols...).DoNothing()` skips conflicts. Target and action are
  mandatory for upsert; duplicate or unknown columns return `ErrInvalidQuery`.
  Calling a conflict method on `Insert` also enables upsert; partial conflict
  configuration is rejected, never silently ignored.
- Consecutive rows with identical included columns share a statement. Many
  scalar-valued rows use parallel typed arrays and `unnest` in one statement,
  for inserts and upserts, on every executor. PostgreSQL `unnest` flattens
  multidimensional arrays: rows containing array-valued columns instead use
  one multi-row `VALUES` statement, preserving NULL and array boundaries.
  Rows with no included columns each use `DEFAULT VALUES`. Heterogeneous
  optional-column masks require separate statements so defaults apply per row.
- `.Chunk(n)` on an insert caps rows per statement (default 1000); nonpositive
  values return `ErrInvalidQuery`. The size belongs to the built value, so
  `Build` and `Run` agree on it. `VALUES` chunks also respect PostgreSQL's 65535
  parameter limit. Chunked operations are not implicitly transactional: use a
  caller-owned transaction for atomicity. Earlier chunks can commit before a
  later failure. A single homogeneous chunk is one atomic statement.
- `app.Users.Update().Set(col.To(v)...).Where(...)` and
  `app.Users.Delete().Where(...)` work without a primary key. Repeated `Where`
  predicates are conjoined. Without `Where`, `.All()` is mandatory or SQL
  rendering returns `ErrInvalidQuery`; no SQL is sent. Empty updates and
  duplicate or unknown assignments are rejected. Nullable `.To` takes `Null[V]`.
- A write without `Returning()` runs with `Exec(ctx, options...)`, which
  returns affected rows (`int64`). `Returning()` adds `RETURNING` with every
  model column and turns the write into a row query (`One`, `First`, `List`,
  `All`), scanned by the descriptor, including defaults and `BEFORE` trigger
  values. Empty results are non-nil slices.
  Conflicts skipped by `DO NOTHING` return no row. PostgreSQL defines row
  order; there is no positional correspondence guarantee. An error returns
  zero count or nil slice, never partial results. Per-call `ExecMode` overrides
  `WithExecMode` and is passed as the first pgx argument on both execution paths.
- `Build()` renders the one statement `Run` would send. An insert that needs
  several statements (more rows than its chunk size, or rows with different
  sets of optional columns) returns `ErrInvalidQuery` from `Build`; `Run`
  sends all of them.
  Descriptors and builders copy metadata/input slices and are immutable.
- `app.Users.Save(user)` updates the row with the model's primary key:
  every insertable non-key column takes the model's value (generated and
  `ALWAYS` identity columns are not written). `app.Users.DeleteRow(user)`
  deletes it. Both are writes (`Build`, `Returning`); a write that matches no
  row returns `ratel.ErrNotFound`.
- Optimistic locking: `.ExpectVersion(col, v)` on `Update` and `Save` adds the
  version predicate and returns `ratel.ErrStaleVersion` when no row matched.
- `db.CopyFrom(ctx, app.Users, seq iter.Seq[UserInsert])` streams rows through
  COPY without buffering them all. COPY sends one column list: the first row's
  set columns are copied, and a later row that sets other optional columns
  stops the copy with `ratel.ErrMixedCopyColumns` rather than dropping a value;
  an invalid insert stops it with `ErrInvalidInsert`. `db.Copy(ctx, table,
  columns, source)` is the untyped form generated `:copyfrom` queries use.
- Integrity violations of a generated `:exec` query are `*ConstraintError`
  like any write.
- `db.Batch(ctx, items...)` sends several built values in one round trip and
  fills each one's destination in order. Items are `ratel.List(q, &models)`
  and `ratel.One(q, &model)` (`ErrNotFound`, `ErrMultipleRows`) for row
  queries, and `ratel.Exec(q, &count)` for writes and commands (including
  `Save` and `DeleteRow` with their missed-row refusals, and every insert
  chunk). The item function accepts only a value of the matching kind. An item
  that cannot render returns its error before anything is sent. pgx batches use the connection's exec mode,
  so per-call `ExecMode` does not apply.

## Relations

```go
users, err := db.Run(app.Users.Select().
	With(app.Users.Orders.Where(app.Orders.Status.Eq(app.OrderPaid)).
		OrderBy(app.Orders.CreatedAt.Desc()).Limit(5).
		With(app.Orders.Items)).
	WithCount(app.Users.Orders)).
	List(ctx)

err = db.Load(ctx, users, app.Users.Manager)          // any []User, e.g. from a static query

active, err := db.Run(app.Users.Select().Where(app.Users.Orders.Has(app.Orders.Status.Eq(app.OrderPaid)))).List(ctx)
```

### Generated relation contract

A generated relations struct stores independent loaded values and counts:

```go
type UserRelations struct {
    Orders     ratel.Loaded[[]Order]
    Manager    ratel.Loaded[*User]
    OrderCount ratel.Loaded[int64]
}

func (u *User) Orders() ([]Order, error) { return u.R.Orders.Get() }
func (u *User) Manager() (*User, error) { return u.R.Manager.Get() }
```

`Loaded[T]` has private state. Its zero value returns `ErrNotLoaded` from
`Get()` and true from `IsZero()`. `LoadedFrom(value)` marks a successful load.
A loaded to-many value is a non-nil slice, including when empty. A loaded
missing to-one value is nil without an error. A loaded count can be zero;
requesting a count does not mark the corresponding models as loaded.

Every catalog `Relation` with a name becomes a field of the descriptor on its
`from` table and, with its inverse name, on its `to` table; a to-many edge also
gets a `<Singular>Count` field. A relation whose target has no primary key is
not generated. A relation between tables of different schemas exists only on
the foreign-key side, and a many-to-many relation only when both tables and the
join table share a schema: the inverse would make the packages import each
other. A relation name that collides with a model field, `R` or another
relation is a generation error. Each table has an unexported base
`WriteTable` (`<descriptor>Base`) without relations; relations target bases, so
mutually related descriptors form no initialization cycle.

Generated descriptors construct each edge with
`NewRel(target, cardinality, keys, attach, options...)`:

- `target` implements `RelationTarget[R]` by embedding `Table[R]` or
  `WriteTable[R, I]`. It is a physical, schema-qualified table with primary-key
  metadata, not a SELECT or static query. `RelOne` allows at most one result
  per parent; multiple matches return `ErrMultipleRows`. `RelMany` allows any
  number of results.
- Each `RelKey[M]` supplies `Column`, the target foreign-key column, `Type`,
  its schema-qualified scalar PostgreSQL type, and `Values func([]M) any`.
  The projection returns a native typed array in input order, with exactly
  one element per input model, just like insert-field array projections.
  Nullable keys use pgx-native nullable array elements. Composite keys are
  parallel arrays in declared component order. No runtime reflection or
  string encoding of keys is used. `Parent` names the parent's own key column,
  which `Has` correlates on.
- `rel.Has(cond)` is a `Cond[M]` on the parent: a correlated
  `EXISTS (SELECT 1 FROM <target> AS "h0" [JOIN <through>] WHERE <keys> AND
  <rel.Where predicates> AND <cond>)`. Nested `Has` take deeper aliases
  (`h1`, ...). A key without `Parent` renders `ErrInvalidQuery`.
- `attach func(*M, []R)` assigns `LoadedFrom(children)` to the generated
  model's `R` field. For to-one edges it maps an empty slice to nil and a
  singleton to `&children[0]`.
- `RelCount[M, R](func(*M, int64))` supplies the independent generated count
  assignment. `WithCount(rel...)` requests it; `rel.Count()` is the equivalent
  projection for `db.Load(ctx, models, rel.Count())`.
- `Through[M, R](schema, table, targetColumns...)` supplies a join table.
  `RelKey.Column` then addresses that table's parent-side FK. The ordered
  `targetColumns` match the target's primary-key columns, including composite
  target keys. All tables and PostgreSQL types remain schema-qualified.
- Constructor metadata, modifiers and requested-relation slices are copied.
  Descriptors are immutable. SQL-affecting modifiers precompute row/count SQL
  and fixed arguments; each load copies the arguments and projects current
  parent keys. Construction never calls key-projection callbacks.
  Projection and assignment callbacks are generated code and must preserve
  the declared array lengths and field assignments.

### Loading behavior

- Loading is eager and explicit. Models hold no database handle; there is no
  lazy loading.
- `Build()` of a SELECT with `With` or `WithCount` returns the root query only:
  relation queries bind the parent keys, which exist only after it runs. They
  are observed in tests through `rateltest.Recorder`.
- `db.Load` loads relations onto any slice of models, so results of static
  queries get relations the same way builder results do.
- Default strategy: one query per requested relation or count per depth,
  `WHERE fk = ANY($1)` for single-column keys; composite keys join parallel
  arrays through `unnest`. Relations of the same depth go in one `pgx.Batch`.
  The parent-key input uses `WITH ORDINALITY`; its ordinal identifies the
  destination model, preserving duplicate parent keys and NULL FK semantics
  without reflection or Go-key comparability requirements. Row-load SQL orders
  only by the relation's own child order; the loader groups the rows by parent
  ordinal in one stable counting pass, so each parent keeps the child order,
  and rows that arrive grouped are not copied (sorting by parent on the server
  measured slower than the pass). Attachments are capacity-bounded slices of
  one model buffer: appending to one parent's loaded slice cannot overwrite
  another parent's children.
- Each batch and every result cursor closes before the next depth starts.
  Nested relations load before results are attached to parents. Attachments
  happen deepest first, only after the entire graph succeeds. A failed
  `db.Load` leaves existing loaded fields unchanged; builder terminals return
  no partial result. Empty parent slices send no batch, and absent children
  trigger no deeper batch. Each page of `Chunks` is a separate graph load.
- `Limit` and `Offset` inside a relation are per parent, through
  `unnest($1) CROSS JOIN LATERAL (... LIMIT n)`.
- Counts per parent use one batched `GROUP BY` query over the foreign key and
  parent ordinal. Missing groups attach zero. Counts respect child `Where`
  predicates, but ignore child ordering, pagination and nested loads.
- `rel.Strategy(strategy)` selects a SQL strategy for data-specific cases:
  `ratel.Window()` uses `row_number()` partitioned by parent ordinal;
  `ratel.Correlated()` uses a correlated count subquery over the same parent-key
  input; `ratel.Joined()` joins that input to an unpaginated to-one target in
  the depth batch. Joined does not fold child columns into the parent SELECT:
  a descriptor can also be loaded onto an arbitrary slice through `db.Load`.
  The zero strategy uses LATERAL for pagination and a key-input join otherwise.
  Incompatible strategies (`Joined` on to-many or paginated edges, `Correlated`
  on row loads, `Window` on counts) return `ErrInvalidQuery` before their batch
  is sent. Every strategy uses native pgx scanning, never `json_agg`.
- pgx v5.11 `Batch.Queue` accepts `QueryRewriter` but not `QueryExecMode`;
  `SendBatch` always uses `ConnConfig.DefaultQueryExecMode`. Configure that
  setting on executor connections, including pool connections, for eager loads.
  `With`, `WithCount` and `db.Load` reject explicit `WithExecMode` or per-call
  `ExecMode` with `ErrInvalidQuery` before any SQL is sent. Silently ignoring a
  requested protocol mode would be unsafe behind PgBouncer. Plain SELECT and
  write operations retain their per-call exec-mode support.
- Parent filters: `Has`, `HasNone`, `HasCount(op, n)` and `Every`. `Every` is
  true for a parent with no children, as documented on the method.
- A query with `With` returns a type that has no `All` iterator: relations need
  the parent keys first, and loading per row would hold the cursor open. For
  streaming with relations it has `Chunks(ctx, n) iter.Seq2[[]M, error]`, which
  reads parents in keyset pages of `n` and loads relations per page.
- A plain SELECT also exposes `Chunks(ctx, n)`. Pages use ascending composite
  primary-key order and a row-value `>` cursor, never growing offsets. Each
  page's cursor closes before the page is yielded, so a caller can safely run
  another query on the same connection while consuming a page. The original
  offset applies only to the first page; an original limit caps the total
  number of models. An empty final page is not yielded. Nonpositive page sizes,
  missing primary-key metadata and explicit ordering other than exactly the
  ascending primary key return `ErrInvalidQuery` before execution. Custom or
  nullable ordering is not silently replaced. Page reads observe separate
  statement snapshots unless the supplied executor provides a transaction
  with the desired isolation; concurrent writes can change later pages.
- Writes per relation: `Create`, `Attach`, `Detach`, `Sync` on the relation
  descriptor, one statement each. `Sync` (make the set of linked children equal
  a given set) is one statement with data-modifying CTEs (`DELETE` of extra
  links, `INSERT ... ON CONFLICT DO NOTHING` of missing ones), so it is atomic
  on any executor. There are no nested graph writes.
- Loaded relations sit in the model's `R` field; accessors return
  `ratel.ErrNotLoaded` for a relation that was not requested.

## Errors

| Error | Class | Meaning |
|---|---|---|
| `ratel.ErrNotFound` | expected refusal | `One` or `First` found no row |
| `ratel.ErrMultipleRows` | expected refusal | `One` found more than one row |
| `ratel.ErrInvalidQuery` | programming error | invalid descriptor, pagination or chunk ordering |
| `ratel.ErrInvalidInsert` | programming error | empty insert input or missing generated constructor flag; no SQL sent |
| `ratel.ErrStaleVersion` | expected refusal | optimistic-locking predicate matched no row |
| generated `Err<Constraint>` values, `*ratel.ConstraintError` | expected refusal | unique, FK, check, not-null or exclusion violation; carries kind, constraint, table, columns; matched with `errors.Is` and `errors.As` |
| `ratel.ErrNotLoaded` | programming error | accessor of a relation that was not loaded |
| wrapped executor errors | technical failure | driver, network, timeout; the cause stays reachable through `errors.As` |

Write errors map SQLSTATE `23505`, `23503`, `23514`, `23502` and `23P01` to
`ConstraintUnique`, `ConstraintForeignKey`, `ConstraintCheck`, `ConstraintNotNull`
and `ConstraintExclusion`. `ConstraintError` carries `Kind`, `Schema`, `Table`,
`Constraint`, `Columns` and `Cause`; `Unwrap` preserves the original executor
error and `pgconn.PgError`. Generated sentinels are `*ConstraintError` values;
`errors.Is` matches kind and each nonempty schema/table/constraint field.
Generated `ratel.Constraints[M](values...)` table metadata supplies column lists
for named constraints. Without it, only the driver's `ColumnName` is known;
ratel never parses error details for columns or bound values. Constraint errors
are refusals, not technical failures.

ratel does not capture stacks; it never turns an unrecognized failure into a
refusal, including serialization failures, cancellation and connection loss.

## Schemas and tenants

- Generated SQL always qualifies tables with their schema.
- `app.Users.InSchema("tenant_42")` returns the same descriptor for another
  schema with the same structure, for schema-per-tenant layouts. Each schema
  produces distinct SQL text and therefore a distinct entry in pgx's statement
  cache; this is documented, not tuned.

## Not provided

- `COPY TO`, LISTEN/NOTIFY and large objects are not part of the runtime; pgx
  offers them directly.

## Telemetry

ratel builds SQL and scans rows; it emits no spans of its own. Every query,
batch and COPY it sends goes through the executor, so the driver traces them:
set a pgx tracer (for example `otelpgx`) on the connection config of the pool
the executor uses. The operation around a ratel call (a request handler, a
use case) is the caller's span. A span per terminal on top of the driver's
would duplicate the query spans and cost every call allocations.

## Performance gates

- No reflection in scanning; allocations per scanned row are benchmarked
  against hand-written `rows.Scan` on pgx, and the difference is part of the
  benchmark report.
- Every builder and loader function with logic has a benchmark next to its
  test.
- Run the real-driver comparisons from the repository root with
  `go -C tests test -tags integration -run '^$' -bench 'Benchmark(ReadScan|Scanner)' -benchmem`.
  `BenchmarkScanner` decodes the same real pgx row repeatedly, isolating
  per-row scanning from network and query setup. `BenchmarkReadScan` compares
  complete five-row slice reads, including SQL rendering and tracing on the
  builder path. Both compare generated field-address scanning with direct
  handwritten `Scan` calls and report allocations.
- `go -C tests test -tags integration -run '^$' -bench '^BenchmarkRelationLoad$' -benchmem`
  compares complete batched relation loads on the real driver: four parent
  models and five child rows, including empty and composite-key parents.
  The generated path builds SQL, scans through generated field
  addresses and attaches loaded values; the handwritten baseline uses the
  same ordinal-key join in one `pgx.Batch` and scans and attaches directly.
- Compare changes with ten samples from each revision, using identical commands:
  `go test -run '^$' -bench '^BenchmarkValueCodec$' -benchmem -count=10` and
  `go -C tests test -tags integration -run '^$' -bench '^(BenchmarkReadScan|BenchmarkRelationLoad)$' -benchmem -count=10`.
  Feed the saved outputs to `benchstat before.txt after.txt`. Driver baselines
  also use ratel nullable values, so codec improvements affect both paths.
  For allocation and CPU attribution, add `-memprofile` and `-cpuprofile`
  output paths; inspect allocation sites with
  `go tool pprof -alloc_objects -list 'PlanScan|scanValue|readRelated|qualifiedColumn' <binary> <memory-profile>`.
  Keep profiles and benchmark output outside version control.
